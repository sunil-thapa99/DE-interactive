Snowflake + AWS

What it is: A cloud-native data warehouse (compute and storage scaled independently) commonly paired with AWS S3 as a raw data source for ingestion pipelines.

Why use it: Near-zero-maintenance scaling, pay-per-second compute, native support for semi-structured data, and built-in features (Snowpipe, Streams, Dynamic Tables, secure data sharing) that replace a lot of infrastructure you'd otherwise have to build yourself.

Covers: S3 ingestion via Snowpipe, three ETL orchestration patterns (Tasks+Streams, Dynamic Tables, dbt+Airflow), architecture & performance, governance, data modeling, and interview Q&A.

Available now 📡

Apache Kafka

What it is: A distributed event streaming platform for publishing, storing, and processing continuous streams of records in real time.

Why use it: Decouples producers from consumers at high throughput/low latency, and is the de facto backbone for real-time pipelines and event-driven architectures across most modern data stacks.

Covers: The distributed log, topics/partitions/offsets, producer durability & ordering knobs, consumer groups & rebalancing, replication & ISR, exactly-once & transactions, Connect/Schema Registry/Streams, production ops & tuning, and interview Q&A.

Available now 🔥

Apache Spark + PySpark + Databricks

What it is: A distributed compute engine for processing large datasets across a cluster, programmed via the DataFrame API (PySpark/Scala/SQL), most commonly run on the Databricks platform with Delta Lake as its storage layer.

Why use it: Handles data volumes and transformation logic too large or too custom for pure SQL — arbitrary code transforms, ML feature engineering, and a single unified engine spanning batch and streaming, unlike a single-node tool like pandas.

Covers: A hands-on Databricks Community Edition pipeline, Python/PySpark fundamentals, the DataFrame API, architecture & performance tuning (shuffles, caching, AQE, skew), Structured Streaming, Delta Lake, Spark-vs-Snowflake trade-offs, and interview Q&A.

Available now 💫

Databricks & the Lakehouse

What it is: The unified Lakehouse platform — Delta Lake storage, Spark/Photon compute, Unity Catalog governance, Workflows & Delta Live Tables — running over your cloud's object store, serving batch, streaming, ML, and BI from one governed copy of the data.

Why use it: Collapses the two-tier lake + warehouse into one open, governed tier; a Databricks-shop interview tests platform judgment (which compute, Delta internals, DLT quality, Unity Catalog governance, cost levers), not just running a notebook.

Covers: Lakehouse & control/data-plane architecture, clusters & workspace, Spark execution model, Delta Lake (log, MERGE, time travel, OPTIMIZE/ZORDER, CDF), Auto Loader & Structured Streaming, Delta Live Tables & expectations, Workflows vs Airflow, Unity Catalog governance/lineage/PHI, SQL Warehouses & Photon, performance & cost tuning, Databricks-vs-Snowflake/EMR, and senior interview Q&A.

Available now 🏃

Apache Airflow

What it is: A workflow orchestration platform for scheduling and monitoring pipelines defined as code (DAGs).

Why use it: The standard choice when a pipeline needs to coordinate multiple systems (not just one warehouse), with retries, dependency management, and observability built in.

Covers: DAG authoring (TaskFlow, dynamic mapping), scheduling & the execution_date gotcha, backfills & idempotency, sensors vs. deferrable operators, XComs, executors & concurrency, and interview Q&A with follow-ups.

Available now ☁️

AWS Data Services

What it is: The AWS lake-house stack a DE actually builds on — S3 as the lake, Glue for serverless ETL & the shared catalog, EMR for managed Spark, Lambda for event-driven glue, and Redshift as the MPP warehouse.

Why use it: Storage decoupled from compute means many engines over the same S3 files, paid for independently; knowing which service owns which job (Glue vs EMR, Athena vs Redshift) and its cost levers is core AWS-DE judgment.

Covers: The reference architecture & service-selection decisions, S3 layout/formats/lifecycle, Glue catalog/crawlers/jobs/bookmarks, EMR cost control, Lambda limits & orchestration, Redshift DISTKEY/SORTKEY/COPY/Spectrum, Redshift-vs-Snowflake, cross-cloud (ADF, BigQuery), and interview Q&A.

Available now ☁️

Azure Data Services

What it is: The Azure lake-house stack a DE actually builds on — ADLS Gen2 as the lake, Data Factory for orchestration & ingestion, Databricks for the heavy transform, and Synapse for warehousing & serving BI.

Why use it: Azure has more overlapping services and blurrier names than AWS, so knowing which tool owns which arrow (ADF orchestrates, Databricks computes, ADLS stores, Synapse serves) and its cost levers is core Azure-DE judgment — and Azure shops are common in enterprise.

Covers: The reference architecture & four-way service decision, ADLS Gen2 (HNS, layout, RBAC/ACLs/Managed Identity, tiers), ADF (Copy vs Data Flows, Integration Runtimes, metadata-driven pipelines, triggers/incremental copy), Databricks (secure ADLS access, Unity Catalog, cluster cost), Synapse (dedicated vs serverless, hash/replicate distributions, Fabric), cross-cloud (AWS/GCP), and interview Q&A.

Available now 🔧

dbt (data build tool)

What it is: The transformation layer of the modern data stack — the "T" in ELT. SQL SELECTs plus software engineering (version control, a testable dependency DAG, data tests, docs/lineage) that turn raw warehouse tables into trustworthy models, executed by the warehouse.

Why use it: It replaces untested, warehouse-locked stored procs and ad-hoc SQL scripts with modular, tested, documented, environment-portable transformations — and it's the tool most analytics-engineering roles are built around.

Covers: Models/ref/sources & the DAG, materializations, incremental models & strategies, testing (generic/singular/unit), snapshots (SCD2) & seeds, Jinja/macros/packages, project layering (staging/intermediate/marts), deployment & Slim CI (state:modified/defer), docs/lineage/exposures, contracts & governance, the semantic layer, and interview Q&A with answered follow-ups.

Available now 🐍

Python for Data Engineering

What it is: The DE lingua franca — the language your pipelines, transforms, orchestration glue, and PySpark jobs are written in, focused on what interviewers actually test rather than general Python trivia.

Why use it: The coding screen and the "make this not fall over on a big file" questions turn on generators, vectorization, memory, and testable transforms — the difference between a script and a production pipeline.

Covers: Core language (data structures & complexity, comprehensions, generators, context managers, decorators, gotchas), pandas (vectorization, chunking, dtypes/memory, when it breaks down), performance (streaming, the GIL, profiling, Parquet), testing (pytest, pure transforms, mocking IO), and interview Q&A.

Docker, Kubernetes & CI/CD

What it is: The deploy story for data work — containerizing jobs with Docker, running batch on Kubernetes, shipping pipelines through CI/CD, and provisioning infra as code.

Why use it: "How do you actually ship and run this?" separates someone who edits jobs by hand from someone who treats pipelines as reproducible, tested, rollback-able software.

Covers: Docker (layers/caching, multi-stage, slim/non-root images, a real job Dockerfile), Kubernetes (pods/deployments, Jobs & CronJobs, requests/limits, Airflow/Spark on K8s, when not to), CI/CD (tests, staged promotion, gated deploys, rollback, GitHub Actions), infra as code (Terraform), and interview Q&A.

Power BI & Tableau

What it is: The BI & visualization layer from a data engineer's seat — modeling the warehouse so dashboards are fast, and understanding the two dominant BI engines well enough to serve and secure them.

Why use it: A DE owns the model BI sits on; the interview turns on star-schema-for-BI, import vs DirectQuery, row vs filter context, and per-user security, not on dragging fields onto a canvas.

Covers: Modeling for BI (star schema, grain, date dimension, many-to-many traps), Power BI (VertiPaq, import vs DirectQuery, DAX & contexts, dataflows, incremental refresh, RLS), Tableau (extracts vs live, LOD expressions, order of operations), performance, and interview Q&A.

Data Modeling

What it is: The dimensional-modeling round that's its own interview — the star schema, fact & dimension design, slowly changing dimensions, and the methodology trade-offs (Kimball/Inmon/Data Vault/OBT) a DE is expected to reason about, not just recite.

Why use it: Getting the grain or the SCD type wrong poisons every report above it; being able to declare a grain in one sentence, pick the right fact type, and defend star-vs-snowflake is what separates "I moved data" from "I designed the warehouse."

Covers: OLTP-vs-OLAP & the star schema, fact tables (grain, additive/semi/non-additive measures, transaction/periodic/accumulating snapshots, factless), dimensions (surrogate keys, conformed, degenerate/role-playing/junk), SCD Types 0–6 (esp. Type 2 via MERGE), Kimball vs Inmon, Data Vault, One Big Table, and interview Q&A with answered follow-ups.

Data Quality & Observability

What it is: The discipline of making data trustworthy — catching bad data with tests, and knowing the moment something breaks with observability — not the same thing, and a senior DE owns both.

Why practice it: "How do you stop bad upstream data corrupting downstream tables?" is a staple senior question; the difference is treating quality as a system (dimensions, gates, monitors, SLAs) rather than ad-hoc checks.

Covers: The six quality dimensions & test types (dbt tests, Great Expectations, Soda), validation vs reconciliation, the five observability pillars (freshness/volume/schema/distribution/lineage), anomaly detection & non-noisy alerting, SLIs/SLOs, data contracts, and data-incident RCA — each with a model answer and answered follow-ups.

Available now 🛡️

Data Governance, Security & Privacy

What it is: Governing sensitive data — who can see what, how it's protected, and proving where it flows — the controls a senior DE owns, especially with PHI/PII/financial data on the line.

Why practice it: "An analyst needs claims data but must never see the SSN/MRN — how?" and "prove where a PHI field flows end to end" are exactly the questions a regulated-domain interviewer drills; buzzwords fail, concrete controls pass.

Covers: RBAC vs ABAC & least privilege, row/column security, masking vs tokenization vs encryption, secrets management; PII/PHI/PCI & the regimes (HIPAA, GDPR, CCPA, PCI-DSS), classification, encryption & key management, GDPR deletion on an immutable lake, retention; data catalogs, lineage & impact analysis, audit & stewardship, policy-as-code — each with a model answer and answered follow-ups.
